Last updated: 2026-10-09 — Task 128 (strict CSI dispatch). The CSI router now
selects a handler on the whole key (private-marker prefix, intermediate, final
byte) instead of the final byte alone; the routed set is documented in
`csi_dispatch.rs` and everything else with valid grammar is recognised and
ignored (warn-logged, no output). Sequences that used to misroute and are now
recognised and ignored: `CSI Ps + T` (was SD), `CSI Ps # P` (was DCH),
`CSI … $ r` (was DECSTBM), `CSI Ps * x` (was DECREQTPARM), `CSI … $ t` and
`CSI Ps SP t` (were window operations), `CSI Ps " q` (DECSCA) and `CSI Ps q`
(DECLL) (were DECSCUSR), `CSI Ps SP u` (was SCORC), `CSI Ps SP @` (SL; was
ICH), `CSI > SP c` (was DA2) and `CSI ? s` / `CSI ? r` (XTSAVE / XTRESTORE;
were DECSLRM / DECSTBM and failed as Invalid). DECSCUSR now requires its SP
intermediate: a bare `CSI Ps q` is no longer accepted. XTVERSION's canonical
form is corrected to `CSI > Ps q`. New rows: `CSI < u` (kitty pop), `CSI = c`
(DA3), `CSI Ps x` (DECREQTPARM), `CSI > Ps ; Pv m` (XTMODKEYS), `CSI ? Ps n`
(DEC private DSR), DECRARA and DECSCA (not planned), and a combined row for
the other newly-ignored forms. The DECCARA, DECSACE, colour-stack, unscroll,
XTSAVE and multiple-cursor rows now say "recognised and ignored" instead of
describing the old misroutes. tmux DCS passthrough now direct-dispatches only
plain CSI; any prefixed or intermediate CSI goes to the main parser.

Last updated: 2026-10-05 — issue #507 — per-pane OSC 9;4 progress-report
state and indicator implemented, closing the gap previously described in
the `OSC 9 ; 4 ; state ; progress` row below. Progress reports resolve into
a typed `ProgressReport` (`ProgressState` + `percent`) by applying a
parser-level `ProgressUpdate` wire form, preserving the ConEmu/ghostty
value-retention rule where the error, indeterminate, and paused states
leave the percentage unchanged when `v` is omitted. An empty value field
(`4;<state>;`) is treated the same as an omitted one. Neither the ghostty
nor the Windows Terminal reference documents that spelling; it is accepted
deliberately so it is not shown as notification text, which is what the
narrower #502 rule did. An empty state field (`4;`) is still rejected and
stays notification text. State is per-pane,
transported on `TerminalSnapshot` following the `cursor_color_override` /
`pointer_shape` precedent, and rendered as a bar across the top of each
pane inside that pane's own painter pass, contributing a bounded damage
`Region` rather than a full repaint. Indeterminate renders a static
full-width bar — deliberately not animated, since a moving sweep would
break the fixed-rect assumption the damage merge depends on. A hardcoded
15s staleness timeout (matching ghostty) clears a stalled report, checked
from both `build_snapshot()` and the PTY consumer's idle arm (armed for
the exact remaining deadline). Cleared on `s=0`, on RIS, and on DECSTR.
Display is gated by the new `[progress] enabled` config option (default
`true`); recognition and parsing remain unconditional, as issue #502 made
them.

## Overview

Freminal implements approximately **90–92 %** of the escape sequences needed for a fully
compatible modern terminal emulator. All critical bugs identified in the March 2026 audit have
been fixed, and further coverage landed during v0.3.0–v0.7.0 (notably: DECDWL/DECDHL rendering,
blinking text, bell with visual + audible feedback, DECANM/VT52, DECNKM, DECBKM, DECLRMM,
AlternateScroll, IRM, and SGR underline styles with per-underline color).

The remaining gaps are primarily optional features: legacy G1–G3 charset
switching and a handful of niche standard modes (SRM) and DEC modes
(?1034, ?1001 functional effect).

### C0 Mid-Sequence Handling

The VT500 spec requires C0 controls to be executed inline even during CSI/OSC sequence
parsing. Freminal's parser is **ECMA-48 compliant** here: C0 controls (BS, CR, LF, VT, FF,
etc.) encountered mid-CSI are executed inline, and the CSI sequence resumes afterward. This
is verified by unit tests (`c0_bs_inside_csi`, `c0_cr_inside_csi`, `c0_vt_inside_csi`).

## CSI — Control Sequence Introducer

CSI routing is strict (Task 128, `csi_dispatch.rs`): a sequence is identified by its
private-marker prefix (`?`, `>`, `<`, `=`), its intermediate byte (SP, `!`, `$`) and its
final byte together, never by the final byte alone. A sequence with valid grammar but no
route is _recognised and unhandled_: it is warn-logged and produces no output, and it
never falls through to the handler of a different sequence that shares its final byte.

**OSC parsing rules (Task 129).**

- **Terminator:** only the terminator (BEL, or `ESC \`) is stripped from the
  payload. A payload that legitimately ends in `\` keeps it, so
  `OSC 0;C:\ BEL` sets the title `C:\` (129.4).
- **Dispatch:** the OSC number is read from the bytes before the first `;` and
  every target receives its raw body (129.5). A non-UTF-8 byte no longer
  invalidates the raw-payload targets (8, 9, 99, 777, 1337, 1338, 0/1/2/7,
  133). The token targets (4, 10, 11, 12, 22, 52, 104) still tokenise their
  own input and still reject non-UTF-8.
- **Size caps:** 1 MiB per OSC sequence; 64 MiB for OSC 1337 and, since
  Task 148.16, about 1.33 MiB for OSC 52 (129.9). OSC 0/1/2 titles are
  truncated to 4096 bytes (148.10). An over-cap sequence is consumed through
  its terminator, produces no output, and is warn-logged with its introducer,
  cap and length only.
- **Control bytes (129.C5):** ECMA-48 and the DEC VT500 state machine, as
  xterm. CAN (0x18) and SUB (0x1A) cancel the OSC with no output, and the bytes
  that follow are ordinary data. Every other C0 byte except BEL and ESC, and
  DEL, is dropped and does not end the OSC, so `ESC LF \` is still ST. Before,
  any such byte made the OSC `Invalid` and the rest of its payload was printed
  as text. (kitty keeps every byte up to the terminator; no kitty protocol
  carries raw C0 in an OSC, so compliant clients are unaffected.)

**OSC 99 behaviour (Task 138).** Reference for the row above; the key table,
reply formats and freminal's deliberate differences from kitty are in
`KITTY_PROTOCOL_REFERENCE.md`. It has no open conformance gap; the standard
icon names are covered by the leg notes below.

- **Parse (`freminal-common`):** an invalid value for a known key ignores that
  key and the rest of the sequence still applies: `c` and `d` are true for any
  value but `0` (an empty value included, as in kitty), `e` is base64 only for
  `1`, an unparsable `u`, `w` or `o` is ignored, `w` is clamped to `>= -1` (an
  integer beyond the 64-bit range clamps rather than being ignored), and an `f`,
  `n`, `s` or `t` value that is not base64 UTF-8 is ignored. A token with no `=`
  or a key that is not one byte, and an unknown key, are skipped. `i` and `g` are
  sanitised, not rejected: bytes outside `[A-Za-z0-9_+.-]` are removed and the
  result is cut to 512 bytes; an id that is empty afterwards is absent, and `i=0`
  is an ordinary id. `a=` words are edits applied in arrival order from the
  default `focus` (`-report`, `-focus` remove). An unknown `p=` keeps its
  metadata and `d=` and discards its payload. A plain payload that is not UTF-8
  decodes lossily. A decoded `f`, `s`, `n` or `t` value of more than 256
  characters is ignored like an undecodable one (that key only). At most 64
  metadata items per sequence; a rejected sequence is reported to the handler
  (`Notify99Rejected`) so it can abandon its transfer. A sequence whose OSC body
  is over 1 MiB never reaches OSC 99: the OSC accumulator drops it silently (spec
  senders use chunks of 4096 bytes or less); the parser's own 1 MiB guard is only
  reachable by a direct call.
- **Reassembly (`TerminalHandler`):** base64 payloads decode as one stream across
  chunks (chunk-then-encode and encode-then-chunk both work). Scalars (`c`, `o`,
  `u`, `w`, `f`, `g`, `s`) take the latest explicit value, `n` and `t`
  concatenate, `a=` edits accumulate, and defaults apply once at finalisation.
  Chunks with no id share one unidentified slot, which an identified content
  chunk discards while it is accumulating. `p=?`, `p=close` and `p=alive` act at
  once whatever `d=` says and never enter or touch the pending map; an id-less
  close or alive is a no-op. A transfer that overruns a cap, carries invalid
  base64 or whose chunk the parser rejected is tombstoned (its `i=` and `d=` are
  recovered from the rejected chunk), so the rest of it emits nothing; a rejected
  id-less `d=0` chunk tombstones the unidentified slot even when it was empty,
  and a rejected id-less final chunk changes nothing when the slot is empty. The
  caps:
  a notification is 1 MiB in total; title, body and buttons 64 KiB each; icon
  1 MiB; `n=`, `t=` and `a=` entries 64 each; all in-flight notifications
  together 8 MiB (the least recently touched other entries are evicted first).
  The pending map holds 128 ids and evicts the least recently touched entry (a
  dropped transfer's tombstone included), so it never refuses a chunk. A full
  reset (RIS) and turning OSC 99 off discard everything in flight.
- **Finalisation:** C0 controls except LF, DEL and C1 controls are removed from
  title, body and button labels; app name, types, icon names and sound name lose
  LF as well. A title or body over 1024 characters is cut to its first 1024 with
  no marker, after the controls are removed (kitty cuts first and strips later,
  so freminal keeps more printable characters; see
  `KITTY_PROTOCOL_REFERENCE.md`); at most 8 buttons are kept, each cut the same
  way at 256, and a
  label that strips to nothing becomes U+FFFD so the button numbers do not shift.
  An empty title takes the body. A notification with neither is dropped with no
  reply, except that one carrying icon data under a `g=` key only primes the icon
  cache.
- **Display:** the `o=` gate is pane-aware. A pane is focused when its window is
  focused, its tab is active and it is the tab's active pane; it is visible when
  its window is focused and not minimised, its tab is active and no other pane is
  zoomed. `unfocused` shows only when not focused; `invisible` only when not
  focused and not visible. Visibility requires OS-window focus, because
  occlusion of an unfocused window cannot be detected, and minimisation is not
  reported on Wayland. Then `[notifications] osc99_filters` runs (`all` or
  `location:regex`, location `title`, `body`, `app` or `type`; regex search, an
  absent body or app name is matched as the empty string; any match drops the
  notification silently with no reply). Then `routing_osc99` chooses the legs
  from the OS-window focus (`toast`, `system`, `both`, `system_when_unfocused`);
  with the Linux/BSD bus unreachable the system leg is replaced by the toast.
  Transmitted icon bytes are cached under `g=` before the gates run, so a
  suppressed notification still fills the cache (global, least-recently-used,
  64 entries and 4 MiB). A frame's requests (displays, controls, icon primings)
  are routed strictly in arrival order.
- **Toast leg:** a keyed toast with its own lifetime: `w=-1` follows urgency
  (`critical` stays until dismissed as an error toast, `normal` 6 s, `low` 3 s);
  `w=0` and `w>0` stay until dismissed as far as the toast is concerned, and for
  `w>0` the registry enforces the exact deadline (so hovering cannot hold it past
  the deadline). Buttons are rendered and reported 1-based. A body click
  activates, the dismiss square closes, and expiry, eviction past five toasts
  (the oldest that is not waiting to be dismissed goes first) and `p=close` close
  it. An update replaces it in place. A keyed toast closed by `p=close`, an
  enforced `w=` deadline or a gone pane fades out over the 400 ms exit animation
  (ignoring clicks and hover) before it is removed, and its close is reported when
  the fade completes. It shows a hand cursor, with hover and
  pressed fills on its buttons (darker on a light pill). It shows no transmitted
  icon images and plays no sounds. The first `n=` name that is one of the eight
  standard names shows as its bundled-font glyph in the toast's icon slot (Task
  138.C4); any other name is ignored.
- **Linux/BSD leg:** one zbus connection, started when the config can use the
  system leg for OSC 99 or for a legacy category (see "Legacy notifications"
  below). `Notify` carries `app_name` (`f=`, else `freminal`), `replaces_id`
  for an update, `expire_timeout` (-1, 0 or milliseconds), a `default` action plus
  one action per button (only when the daemon has `actions`), and the hints
  `urgency`, `category` (first `t=`), `suppress-sound` for `silent`, `sound-name`
  for a named sound, `image-data` for a transmitted icon, `image-path` for an
  icon chosen from the `n=` names (also sent as `app_icon`; 138.C24) and
  `desktop-entry` (`freminal`). The icon is the first `n=` name that is standard (mapped to its
  freedesktop name) or found in the XDG icon scan (run once on a background
  thread, started by the first lookup: a notification with a non-standard `n=`
  name, or an `f=` and no names or icon data, not at service start), else the transmitted data (decoded as PNG, JPEG, GIF or WebP, at most
  4096x4096 and 64 MiB, EXIF orientation applied, downscaled to fit 256x256), else
  the first name verbatim; with no names, the data, else the `.desktop` icon
  matching `f=`, else freminal's (data that does not decode counts as none).
  `error`, `warn`, `warning`, `info` and `question` become the freedesktop
  `dialog-*` sound names. The body gets a U+200C after `<` and `&` when the
  daemon has `body-markup`. Until `GetCapabilities` answers, `body`, `actions` and
  `body-markup` are assumed and `sound` is not; it is asked again after every
  owner change. `p=close`, expiry and eviction call `CloseNotification`.
  `ActionInvoked` and `NotificationClosed` are believed only from the current
  owner of `org.freedesktop.Notifications` (followed across daemon restarts; an
  owner change closes only the instances recorded under another owner).
  `GetNameOwner` and `GetCapabilities` never D-Bus-activate a daemon
  (`NO_AUTO_START`); every call is bounded at 25 s, and after a timeout shows
  fail without calling the daemon for 30 s. If either signal pump ends, every
  mapped instance is reported closed and the leg becomes unavailable. If the
  session bus cannot be reached the leg is unavailable: it displays nothing,
  `system` routing becomes unsupported, and `both` and `system_when_unfocused`
  fall back to the toast. While the service is unavailable (the connect failed at
  start, or the signals were lost) it reconnects every 30 s on its own timer; no
  notification is needed to trigger an attempt, only the first failure is
  reported, and a reconnect reports the daemon's capabilities (the assumed ones if
  nobody can be asked yet), so the daemon state recovers and the capabilities are
  re-broadcast to every pane.
- **macOS / Windows leg:** fire-and-forget through one delivery thread
  (`freminal-notify-deliver`, a queue of 16; a request that finds it full is
  dropped). macOS uses `notify-rust`; Windows builds the toast directly with
  `tauri-winrt-notification` (the icon is an `appLogoOverride`, no reminder
  scenario). No buttons are registered; activation and close cannot be observed.
  `s=silent` is silent, and `system` or any named sound plays the platform
  default. `w=` is passed as the OS timeout (a short or long toast on Windows,
  ignored on macOS) and is not enforced by freminal. Urgency is not acted on
  there. The icon is an image file in a
  per-process directory (`freminal-osc99-icons-<pid>`, mode `0700`, files named
  by content hash, at most 64, deleted after 10 minutes unused and at exit). On
  Unix an existing directory is used only if it is a real directory with no group
  or other permissions and owned by the current user; on first use, sibling
  `freminal-osc99-icons-*` directories that pass the same checks and are more
  than 24 hours old (left by a killed process) are removed.
  Names come first, as on Linux: the first `n=` name that is one of the eight
  standard names is drawn from the bundled `CaskaydiaCove` glyph to a 256x256 PNG
  (a white glyph on an opaque `#5A5A5A` rounded square tile), so it reads on
  light and dark backgrounds (Task 138.C5). Otherwise a transmitted icon is
  shown, decoded within the limits and re-encoded as a PNG; a name that is not
  standard cannot be resolved there and is ignored. A `c=1` request is answered
  with `p=close;untracked` when the notification is shown, and nothing follows.
  A display on this leg alone is shown, answered and forgotten at once.
- **Legacy notifications (Task 149):** OSC 9, OSC 777, OSC 133 `D`
  command-finished and the Settings "Test Notification" button use the same
  native backend as OSC 99 on each platform, so no platform needs `notify-rust`
  except macOS. They carry a summary, a body and (Linux/BSD only) an urgency,
  and are never tracked: no instance, no events, no buttons.
  - **Linux/BSD:** handed to the zbus service above (the service also starts
    when a legacy category's routing can use the system leg). `Notify` carries
    app name and icon `freminal`, `replaces_id` 0, no actions, expire timeout -1,
    `Critical` urgency for an error and `Normal` otherwise, and freminal's icon
    as `image-data` (downscaled to fit 256x256). The summary and body get a
    U+200C after `<` and `&` when the daemon has `body-markup` (assumed until
    `GetCapabilities` answers). The escaping follows that capability, so a
    daemon that formats text without advertising `body-markup` gets raw text
    (accepted: OSC 99's body behaves the same). At most 16 plain notifications
    are in flight at once, a separate budget inside the service's shared command
    queue so OSC 99 keeps its slots. A notification is dropped when that budget
    or the queue is full, while the daemon is in its 30 s cooldown after a
    timeout, and while the service is reconnecting (up to 30 s after a failed
    connect or a lost connection). Before Task 149 every notification opened its
    own connection, so none was dropped for that reason.
  - **Windows:** a toast built directly with `tauri-winrt-notification`, in the
    same style as the OSC 99 toast: the summary as the title, the body as the
    text, silent, short, no scenario (an error is an ordinary toast).
  - **macOS:** `notify-rust` with app name and icon `freminal`, the summary and
    the body; no urgency.
  - **macOS / Windows delivery:** one `freminal-notify` thread with a queue of
    16 (separate from the OSC 99 thread); a notification that finds it full is
    dropped.
- **Lifecycle:** every notification displayed on a tracked leg becomes an
  instance keyed by pane and `i=`. Update in place, `p=close` and `p=alive` see
  only the requesting pane's instances (kitty's `p=close` looks across windows).
  An update replaces every leg in place and sends no close report for the
  replaced one; a leg the update no longer uses is closed. `p=close` and expiry
  close every open leg. `p=alive` lists an instance while it has an open leg that
  has not been asked to close, so an activated `c=1` instance whose desktop
  notification is still displayed stays listed, as in kitty. A positive `w=` is
  enforced by freminal on every tracked leg, measured from display (an update
  restarts it). Activation from any leg sends the activation report when
  `a=report` is set (empty payload, or the 1-based button number), focuses when
  `focus` is set (switch to the pane's tab, unzoom, make the pane active, raise
  the OS window; a compositor may refuse the raise), and closes the other legs;
  a repeated activation of the same instance is ignored. Without `c=1` the
  instance is then forgotten; with `c=1` exactly one `p=close` report follows
  once every tracked leg has closed. A pane holds at most 32 instances (its own
  oldest is forgotten first) and the registry 128 overall; a forgotten instance
  gets no reply. An instance whose pane is gone is dropped, its open legs are
  closed (the toast fades out, the desktop notification is closed) and no reply
  is sent.
- **`p=?`:** answered on the PTY thread in stream order, so it precedes the
  answer to a DA1 sent after it. The reply follows kitty's key order
  (`a : o : u : p : c : w : s`) and lists only what the routing can honour. Each
  leg has a capability set: the toast has everything except icons and standard
  sound names; the Linux/BSD leg follows the daemon (`actions` gives report,
  focus and buttons, `body` gives body, `sound` gives the standard sound names)
  and always has close events, expiry, urgency and icons; macOS and Windows have
  body and icons only (no urgency on either). `p=close` is
  advertised everywhere, as kitty does. `toast` and `system` use their one leg.
  `both` advertises a feature either leg has (report, focus, urgency, sound
  names, body, buttons, icons) and a per-notification guarantee (close events,
  expiry) only when both have it. `system_when_unfocused` advertises only what
  both legs have, because either may show. With the Linux/BSD bus unreachable,
  `both` and `system_when_unfocused` advertise the toast leg's features (the
  notification routes to the toast), and `system` makes OSC 99 unsupported. With
  notifications, `osc_99` or `routing_osc99` off, OSC 99 is unsupported: every
  request is ignored and `p=?` is not answered. Replies carry sanitised ids and
  honour S8C1T. The `icons` capability is the transmitted `p=icon` image payload;
  the standard icon names are honoured on every leg whatever it says.
- **Platform limits:** macOS and Windows have no activation reports, no close
  tracking, no update in place, no programmatic close, no expiry and no buttons,
  and `p=?` omits what they cannot do. The OS gives a background thread no way to
  observe a notification there, and macOS cannot report a delivery failure. The
  toast plays no sounds on any platform.

## FTCS — FinalTerm Control Sequences (OSC 133)

| Sequence  | Name                  | Status | Notes                                                                                           |
| --------- | --------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| OSC 133 A | Prompt Start          | ✅     | Parsed with `freminal=1; fid=<id>`; stored in `FtcsState` and `CommandBlock`                    |
| OSC 133 B | Prompt End            | ✅     | Parsed with `freminal=1; fid=<id>`; fid used to locate matching block                           |
| OSC 133 C | Pre-execution (input) | ✅     | Parsed with `freminal=1; fid=<id>`; fid used to locate matching block                           |
| OSC 133 D | Command Finished      | ✅     | Parsed with `freminal=1; fid=<id>`; exit code and fid used to close the matching `CommandBlock` |
| OSC 133 P | Prompt Property       | ✅     | Accepted from any emitter (no `freminal=1` required); informational only                        |

**Freminal `freminal=1; fid=<id>` extension:** Freminal extends OSC 133 A/B/C/D with
`freminal=1; fid=<id>` parameters. Markers without `freminal=1` are silently dropped by the
parser to avoid duplicate command blocks when other shell integrations (WezTerm, Starship,
iTerm2, Kitty) are simultaneously active. The `fid` parameter is a per-command correlation ID
that allows `A` and `D` pairs to be matched explicitly rather than by position.
`P` (`PromptProperty`) does not require `freminal=1`. See `Documents/DESIGN_DECISIONS.md`
"Shell Integration Architecture" for the full rationale.

UI for command-block navigation (gutters, jump-to-prompt, fold) is planned for
**Task 72** in v0.9.0 and is not yet implemented.

## Remaining Gaps

The gaps that remain are either low-priority polish or require significant new infrastructure:

1. **SO/SI G1 charset switching** — Consumed as control characters; G1 rendering not implemented (simplified single-slot charset model).
2. **OSC 66** — Kitty text sizing is not implemented; the handler is a vestigial no-op that silently consumes the sequence (Task 104, v0.13.3). It is not a Contour code. DECRPM ?2031 is the functional adaptive-theme path. OSC 777 is now implemented (Task 76).
3. **Standard mode SRM (12)** — Rare in practice.
4. **?1034 (Interpret meta key)** and **?1001 functional hilite tracking** — Niche.
5. **OSC 133 command-block UI** — Markers parsed; navigation/gutter UI planned for Task 72 (v0.9.0).
6. **Kitty protocol compliance (v0.13.x)** — graphics and keyboard are partially conformant (OSC 99 is conformant, Task 138), and OSC 21 / 22 / 72 / 5113 / 5522, the colour stack, unscroll, DECCARA, XTSAVE and multiple cursors are missing or incomplete. See the 2026-10-08 audit in `PLAN_VERSION_130.md` (Tasks 102–105, 126–146).
